Tech Jobs Radar

A job board for tech vacancies in the Netherlands, read directly from employers' own career sites, with every posting classified and tagged.

Overview

Tech Jobs Radar is a live job search site for tech, software, data and IT vacancies in the Netherlands, collected directly from employers' own career sites. Each posting is classified and annotated with structured fields: required skills, seniority, experience, degree, posting language, whether Dutch is required, visa sponsorship and remote policy. Every listing links back to the employer's original page, and optional accounts keep a profile and saved jobs across devices.

Architecture

sources -> queue -> workers + adapters -> normalise, filter, dedup -> classify, extract -> Postgres -> API -> site
  • Ingestion. Source adapters for the public job board APIs of common applicant tracking systems (Greenhouse, Lever, Ashby, Workable, Recruitee, Teamtailor, Personio, Workday, SmartRecruiters and others), plus schema.org JobPosting data read through careers site sitemaps. New boards are discovered through the Internet Archive's URL index and the IND register of recognised sponsors.
  • Crawling. A Redis queue (RQ) with worker processes, one job per board, with per-host rate limits shared across all workers and robots.txt respected.
  • Processing. A Netherlands-only filter, duplicate linking, posting lifecycle tracking and periodic link checks, followed by a rule-based classifier and extractor that fill a typed schema.
  • Serving. A FastAPI JSON API with a response cache, and a plain JavaScript front end with Chart.js and D3.

Every adapter maps a board's response to the same raw posting record, so the rest of the pipeline is independent of the source. The crawl steps are plain functions, so the same code runs in a queue worker, in a single local process and in the tests.

Data pipeline

Crawl scheduling

Crawl frequency adapts to each source's recent yield of Dutch postings, and sources that repeatedly fail are disabled. Rate limits are counted per host in Redis, so all workers draw on one budget, and boards on a shared multi-tenant platform share one limit because such platforms rate-limit by IP. robots.txt is matched with longest-rule precedence, as major search engines do, rather than the first-match behaviour of Python's standard parser. Periodic jobs are queued from a scheduler thread inside the worker, which claims each time slot in Redis so that several workers never queue the same run twice.

Lifecycle and deduplication

Each posting is normalised into canonical fields, including a duplicate key and a content hash; classification and extraction run only when the posting is new or its hash changes. Postings that disappear from a board are closed, with a guard that treats a sudden sharp drop in a board's postings as a partial response.

Duplicates are linked to one canonical posting rather than deleted, by rules covering the same vacancy on several sources, reposts, per-city copies of one vacancy and Dutch and English versions of the same posting. The employer's own copy is preferred over an agency's. Dutch and English copies are paired one-to-one, using title similarity and shared numbers such as salary and hours, so that two Dutch jobs cannot collapse onto one English job.

Classification and extraction

The tech classifier scores job titles by rules, with an exclusion list for non-technical functions and phrases that keep a title technical despite an excluded word ("Sales Engineer"). Generic titles such as "Engineer" or "Analyst" count as tech only when the role text describes hands-on software, IT or data work.

The extractor fills a typed Pydantic schema. It first segments a posting into the job description and the company description using Dutch and English section headers, and reads skills only from the job part, since company introductions often name the employer's own products. Requirements are parsed clause by clause, so that "Dutch is a plus" is not a Dutch requirement, office days in the same sentence turn "remote" into hybrid, and negation applies only within its clause. The rules are versioned, so stored postings can be re-extracted after a change. The rule-based extractor serves as a cheap, deterministic baseline that any LLM extractor would have to beat on the golden set.

Evaluation

The extractor is scored field by field against a hand-corrected golden set of 46 postings: exact match for scalar fields and precision, recall and F1 for skill lists. This evaluation runs in CI on every push as a quality gate, and the build fails if the mean of nine field accuracies and the skills F1 falls below 0.70.

A second gate measures the site's filters on 500 live postings, split into 300 for tuning the rules and 200 held out for scoring only. Each filter is measured as it is used, with 95% confidence intervals; for the "English, no Dutch required" filter, for example, the share of shown jobs that need no Dutch. Since tech role classification is heavily imbalanced, with some rare categories, scores are tracked per field rather than as a single number.

Deployment

Production runs on k3s on a single AWS EC2 instance within a 2 GB memory budget, packaged as a Helm chart, with the AWS resources defined in Terraform. GitHub Actions runs the tests and evaluation gates on every push and builds an image tagged with the commit. Flux then deploys the release from Git in a GitOps workflow and rolls it back if the new pods do not become ready. Prometheus collects metrics, an alert fires when crawl volume drops, and the database is backed up to S3 nightly.

Data and terms

Only public job board APIs and careers pages are read. LinkedIn, Indeed and Glassdoor are excluded, as their terms prohibit automated access, as are aggregators and sites that block the crawler. Contact details are removed from posting text before storage.
