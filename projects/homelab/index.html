Personal project · in daily use

Self-hosted app platform

A platform of more than ten small web apps I built for my own daily use (cooking, language learning, fitness, reading), each applying a language model to a specific job and running on hardware I host and administer myself.

Summary

  • A platform of more than ten containerised web apps I designed, built and run on a home server, each reached through a single sign-on and installable on my phone as its own app.
  • LLMs are used for specific jobs (understanding language, classifying it, and extracting structured fields), running locally on an Ollama server (Llama 3.1, structured JSON output), with optional fallback to hosted models (Claude, Gemini, Amazon Bedrock) under a per-task budget.
  • A deliberate split throughout: the model does only language, classification and extraction, while every number, score and prediction is computed in deterministic, testable code.
  • Each push to main is built, deployed and health-checked automatically in a GitOps workflow, with Docker Compose per app, a reverse proxy and per-app data that survives every deploy.

Overview

This is the software I run for myself, outside my studies and job applications. Over time it has grown into a small platform of more than ten web apps on one home server: a kitchen assistant that tracks a pantry and suggests meals from what is in it, a Dutch speaking-practice tutor, a recommender for local deals, a daily job-search agent, a voice-first notebook, health and fitness trackers, and a notification router that ties them together. Each is a separate app, but they share one login, one design language and one set of back-end services.

I treat it as a place to build and operate real systems end to end. It is software I depend on every day, so it has to stay up, keep my data safe and run cheaply on a single machine.

The server and the deployment setup are shared with my collaborator Ralph Warrand, and a few of the apps and shared services are built together. The rest are my own.

The apps

  • Kitchen assistant. Pantry inventory, barcode scanning and voice input, meal suggestions from current stock, and nutrition tracking against food databases. The model reads free text into foods and quantities; the nutrition maths is done in code.
  • Dutch tutor. A spoken-conversation partner that corrects and explains my sentences, with spaced repetition over my own mistakes. Speech is handled on-device by local models (speech-to-text and text-to-speech), and the conversation runs on a local LLM.
  • Deals recommender. Collects local offers and ranks them against my learned taste using text embeddings from the local model, rather than asking the model to choose.
  • Job-search agent. Crawls job sources on a daily schedule and scores each listing against my own requirements, requirement by requirement. The model judges whether each requirement is met, and the final score is computed in code rather than by the model.
  • Deterministic by design. Several apps, such as the fitness and cycle trackers, use no LLM at all: their predictions and summaries are plain, testable functions. Choosing where a model does and does not belong is part of the work.

Running the models

The default engine is a shared Ollama server holding one model at a time (Llama 3.1, 8B). Anywhere code reads the answer, the model is asked for structured JSON against a schema, so its output can be parsed and validated rather than scraped from prose. An app can be pointed at a stronger hosted model (Claude, Gemini or Amazon Bedrock) for tasks where the local model is not good enough; those calls run under a monthly budget and fall back to the local model when it is exhausted, with the cost of each task logged.

The principle I keep to across every app is that the language model is for language: understanding text, classifying it and extracting fields. Everything that can be computed (sums, dates, nutrition, scores, predictions) is done in ordinary code, which is testable and cannot hallucinate. It makes the apps more reliable and their output explainable.

How it is deployed

git push -> CI (Gitea Actions) -> Docker build -> deploy -> health check
  • GitOps. A push to an app's main branch triggers a pipeline that builds the image, deploys the new container and checks its health; a failed health check is visible on the commit. Nothing is deployed by hand.
  • Separation of code and operation. How each app runs (its port, environment, mounts and network) lives in a separate Docker Compose definition, not in the app's own repository, so a change to application code can never alter its privileges or storage.
  • Routing and access. A reverse proxy is configured from container labels and reloaded without downtime; a single sign-on (SSO) layer sits in front of everything and passes each app a trusted user identity, so every app keeps per-user data without implementing its own login.
  • State and secrets. Each app keeps its data in a volume that survives deploys; secrets live in environment files on the host and are never committed. Scheduled jobs run on a timer, and health is watched with push notifications when something goes down.

What I take from it

Running this has taught me the parts of the job that a notebook does not: containerising and deploying services, keeping them observable and recoverable, working within a tight memory and cost budget, and making deliberate choices about which tasks suit a language model and which are better done in code. It is also simply useful: I reach for these apps every day.
