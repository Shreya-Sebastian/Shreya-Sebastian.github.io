Software Architecture · TU Delft

Fault-tolerant sensor ingestion

Smart home sensor data that survives network outages: local buffering, chunked resynchronisation and a message queue, tested under failures and load.

Context

For the Software Architecture course our team designed a smart home system that learns household routines from sensor data. One of its key quality requirements is that no sensor data is lost when the home's network connection drops. I built the proof of concept that tests this part of the architecture, and wrote the report sections on it.

Architecture

  • Ingestion server. A FastAPI service with a POST /ingest/ endpoint that accepts a batch of readings, validates them with Pydantic (reading id, sensor id, type, value, timestamp) and publishes each one to RabbitMQ. It returns 503 when the broker is unreachable, and has a health endpoint.
  • Message queue. A durable RabbitMQ queue with persistent messages, so readings survive a broker restart.
  • Consumer. Reads one message at a time and acknowledges it only after processing, with automatic reconnection.
  • Sensors. Each simulated sensor writes unsent readings to a local log file, so the buffer also survives a restart of the sensor.

Buffering and resynchronisation

When a send fails, the sensor marks itself offline and appends the reading to its buffer. Once the connection is back, it sends the backlog oldest first in chunks of 25 readings, removing items only after the server has accepted them, and then sends the current reading. A failed chunk leaves the buffer untouched and in order, so nothing is lost or reordered.

Testing

  • Fault scenario. A three-phase run with five sensors: normal operation, a disruption in which three sensors go offline while the others keep sending, and resynchronisation. It passes when every disconnected sensor has emptied its buffer.
  • Error handling. Unit tests with mocked HTTP responses check that buffers are reloaded on start, that connection errors and 503 responses lead to buffering, and that chunked resynchronisation keeps order whether a chunk succeeds or fails.
  • Load. Tests against a live server send 5,000 readings in one request, 200 concurrent requests, and a sustained stream of 1,000 messages from 50 sensors.

CI

A GitLab CI pipeline runs in three stages: a style stage (compilation check and black), a build stage that builds the Docker image and pushes it to the GitLab container registry, and a test stage that runs the error-handling tests, the load tests and the fault scenario inside that image against a RabbitMQ service.
