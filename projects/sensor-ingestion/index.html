Software Architecture · TU Delft

Fault-tolerant sensor ingestion

Smart home sensor data that survives network outages: local buffering, chunked resynchronisation and a message queue, tested under failures and load.

Context

For the Software Architecture course our team designed a smart home system that learns household routines from sensor data, split into a local hub and a set of cloud services. The proof of concept tests one part of that architecture: delivering sensor readings to the backend without loss when the home's network connection drops. I built most of the proof of concept and wrote the report sections on it.

It targets the design's availability and scalability goals, and two problems in particular: data loss during outages, when a sensor sends directly to a server, and tight coupling, when a slow processor stalls ingestion. Availability is defined as sensors continuing to produce readings while disconnected, with every reading reaching the queue once the connection returns.

Architecture

  • Ingestion service. A FastAPI REST endpoint that accepts batches of readings, validates them against a Pydantic schema and publishes them to RabbitMQ, returning 503 when the broker is unreachable. Its role is kept minimal (accept, validate, forward), so malformed data never enters the queue.
  • Message queue. A durable RabbitMQ queue with persistent messages decouples ingestion from processing, absorbs bursts and survives broker restarts.
  • Consumer. Uses manual acknowledgement after processing, so unacknowledged messages are requeued, and scales horizontally as competing consumers on the same queue.
  • Sensors. Simulated sensors implement store-and-forward with a persistent local buffer that survives a restart.

The broker, ingestion service and consumer run as separate containers under Docker Compose.

Transport choice

The report compares four transports between sensors and the ingestion service:

ProtocolForAgainst
RESTFirewall friendly; simple request and response with explicit chunked backlog upload; easy validation and backoffMore overhead per message than MQTT; not a push protocol
MQTTDesigned for IoT; persistent sessions; low bandwidth and battery useNeeds a broker; more moving parts; ordering subtleties at scale
WebSocketsLow latency; server push; full duplexNeeds backpressure and reconnection logic; harder to batch
UDPLightweight; suits constrained networksNetwork traversal; harder to observe

REST was chosen for its ease of handling and its suitability for a smart home application.

Buffering and resynchronisation

On a connection or server error the sensor goes offline and appends readings to its buffer. On reconnection it drains the backlog oldest first in fixed-size chunks interleaved with live data, removing items only after the server accepts them. This keeps ordering, guarantees no loss, prevents a long-offline sensor from overloading the server and limits retries to the remaining chunks.

Testing and CI

  • Fault injection. A three-phase scenario with five sensors (normal operation, a disruption in which three go offline, then resynchronisation) passes when every disconnected sensor has emptied its buffer; a second scenario uses overlapping disconnections.
  • Unit tests. Mocked HTTP responses verify buffering on connection errors and 503s, buffer recovery on start, and order preservation during chunked resynchronisation.
  • Load tests. Against a live server: 5,000 readings in one request, 200 concurrent requests, and a sustained stream of 1,000 messages from 50 sensors, each requiring every request to be accepted.

A three-stage GitLab CI pipeline runs style checks, builds and pushes the Docker image to the container registry, and runs the unit, load and fault tests inside that image against a RabbitMQ service.

Scope

The sensors are simulated and the consumer only acknowledges messages. Next steps in the report are forwarding readings for analysis and storage, and device authentication.
